# ADR-0003: The web app is a React single-page app on Vite, with a generated API client

**Date**: 2026-11-05
**Status**: accepted
**Deciders**: Marco Scalzo

## Context

Players and staff use the app mostly from a phone. The app needs a web interface that the team can build and test with tools it already knows, and whose calls to the API stay in step with the backend.

## Decision

The web app is a React single-page app in TypeScript, built with Vite, on Node 22. It uses TanStack Router for routes, TanStack Query for server state, Tailwind CSS for styles, and `openapi-fetch` with types generated by `openapi-typescript` from the API's OpenAPI document (`frontend/src/lib/api/schema.d.ts`, committed and checked in CI). Tests run with Vitest and Playwright; ESLint and Prettier keep the code consistent.

## Alternatives Considered

### Alternative 1: Next.js with server-side rendering
- **Pros**: server rendering, routes and API in one framework
- **Cons**: a second server runtime next to FastAPI, more moving parts to deploy
- **Why not**: the app needs no SEO and no server rendering; a static build behind nginx is simpler

### Alternative 2: Server-rendered pages from FastAPI (Jinja, htmx)
- **Pros**: one language, no build step for the interface
- **Cons**: richer interactions get harder; the team's front-end experience and checks are on React
- **Why not**: the team already knows React and its test tools

## Consequences

### Positive
- A change to an API route that breaks the web app fails the type check
- A stack the team already knows, with mature test tools

### Negative
- `schema.d.ts` and `routeTree.gen.ts` are generated files to regenerate and commit

### Risks
- The generated types drift from the API. Mitigation: the `ui-api-types` job and the pre-commit hook compare them with the API
